# 背景与验证问题

## 背景与这份计划为什么存在

- **学校 / 年级**：浙江财经大学计算机专业，大三。
- **当前基础**：Java 后端只学过一些皮毛，没有形成完整工程能力，也没有长期坚持下来。
- **就业目标**：优先争取本科直接就业；大学期间主要在 **杭州刷实习**，毕业后倾向 **回温州工作**。
- **地域约束**：温州制造业、电气、汽配、装备等企业较多，因此希望未来技能不仅能在杭州找到实习，也能迁移到温州的制造业数字化、工业软件、设备联网等场景。
- **最初的转向想法**：曾在 LINUX DO 看到“机器人应用后端”建议，路线大致是 **Python + Agent + 机器人应用基础**；随后一度扩展成 FastAPI、asyncio、MQTT、ROS2、LangGraph、MCP 等一整套技术栈。
- **经过复盘后的修正**：不再默认“从 Java 换到 Python / 机器人 / Agent 就能解决学不下去”。机器人机上软件、机器人云端后台、Agent 应用开发，本来就是不同岗位；对本科阶段来说，同时堆 ROS2 + Agent 容易摊得太宽。
- **当前更现实的主假设**：如果未来仍做开发，更值得先验证的是 **通用后端能力 + 工业 / 设备场景**，而不是直接把自己定义成“机器人 Agent 工程师”。
- **兴趣上的关键疑问**：自己可能不只是“不喜欢 Java”，而是同时不喜欢：
  1. 商城 / 网站这一类纯业务题材；
  2. 长时间只在屏幕里写逻辑、看不到任何现实对象产生变化。
- **因此这份计划不是职业定案**：它是一个低成本的 4 周实验，用来判断“代码连接设备”是否真的比传统 CRUD 更能提供持续动力。
- **现有硬件条件**：目前只有 **Windows 电脑**，没有树莓派、ESP32 或真实机器人；因此第一阶段全部用 **Python 虚拟设备**模拟，不为验证兴趣先买硬件。
- **语言选择**：这 4 周统一用 **Python**，不是因为 Python 天生比 Java 更适合就业，而是为了降低试验成本、快速写出 MQTT 设备模拟器和 FastAPI 后端。
- **暂不主攻的方向**：ROS2、Gazebo、Nav2、LangGraph、MCP、RAG 等先冻结。只有这个小项目做完后，确认自己真的喜欢设备软件，再决定是否往工业 IoT、设备集成、ROS2 机器人或 Agent 延伸。
- **对温州就业的当前判断**：相比把“具身智能 / 机器人应用后端”当唯一方向，**工业软件、MES/WMS 周边、设备联网、制造业信息化、IoT 后端、设备集成**与“杭州实习 + 回温州”的迁移路径更自然；但这也不等于现在就把自己锁死为 MES 工程师。
- **对“要看见实物”的进一步判断**：工业后端依然会有大量 API、SQL、业务逻辑和调试。如果连“网页命令 → MQTT → 设备状态变化”这种反馈都觉得无聊，那么下一步应评估的是 **实施、现场集成、自动化、PLC、技术支持等更靠近现场的岗位**，而不是继续换框架。
- **不可误判的点**：Windows 虚拟设备只能验证“是否喜欢设备软件这一层”，不能完全验证“是否喜欢碰真实硬件 / 现场”。如果 4 周后明显更有兴趣，再花几十元买 ESP32 或尝试 ROS2，会更有意义。

## 这 4 周真正要回答的问题

> **我是不喜欢 Java / 商城，还是其实不喜欢软件开发本身？**  
> **当代码能影响一个“设备状态”时，我是否明显更愿意继续做？**

核心原则：**先闭环，后补技术；20% 学、80% 做；视频是字典，不是进度条。**
